# Malga sandbox testing

Malga's sandbox (`sandbox-api.malga.io`) lets you test the full integration without real money movement. It is keyed by sandbox credentials (different from production). This skill consolidates everything a QA needs in one place.

References:
- Test guide: <https://docs.malga.io/documentations/welcome/testing>
- SDK sandbox docs: `sdks/api-sdks/docs/sandbox/` (changeChargeStatus, changeAntifraudStatus, generateCard)
- Postman collection: <https://www.postman.com/joint-operations-engineer-24793538/sandbox-malga/collection/34oyc6z>

## Base URL

```
https://sandbox-api.malga.io/v1/
```

The same routes as production. The merchant's sandbox `X-Client-Id` and `X-Api-Key` differentiate the environment. The Node SDK accepts `options.sandbox: true` and handles the URL switch automatically.

## Test cards — the last-digit rule

Sandbox card numbers can be generated by any test-card generator. Behavior is determined by the **last digit** of the card number:

| Last digit | Outcome | Final status |
|---|---|---|
| 0, 1, 4 | Approved | `authorized` (or `pre_authorized` with `capture: false`) |
| 2 | Declined | `failed` |
| 3 | Expired card | `failed` |
| 5 | Blocked card | `failed` |
| 6 | Timeout | `failed` |
| 7 | Canceled card | `failed` |
| 8 | Random — approved or timeout | `authorized` or `failed` |

CVV validation in sandbox:
- CVV ending in `0` → validated.
- Any other CVV → returns "not validated" (useful for zero-dollar testing).

Tokenized cards behave the same way (the test-card rule is preserved through tokenization).

## Forcing a charge status (Pix, Boleto, async flows)

For methods that settle asynchronously (Pix, Boleto), the sandbox lets you manually push a charge to a target status:

```bash
POST https://sandbox-api.malga.io/v1/charges/<CHARGE_ID>
Headers: X-Client-Id, X-Api-Key
Body:
{ "status": "authorized" }
```

Supported manual transitions:
- For **Pix**: `authorized`, `voided`, `refund_pending`, `charged_back`.
- For **Boleto**: `authorized`, `voided`, `charged_back`.
- For **Credit**: `authorized`, `voided`, `charged_back`.

This triggers the corresponding webhook event (e.g., `transaction.authorized`). Use it to validate the receiver's signature verification, idempotency handling, and queue processing.

The Node SDK exposes this as:

```ts
await malga.sandbox.changeChargeStatus({ chargeId, status: 'authorized' });
```

## Forcing antifraud outcomes

The antifraud sandbox is driven by the **last digit of the customer document** sent in `fraudAnalysis.customer.identity` (or equivalent):

| Document last digit | Decision | DeclinedCode |
|---|---|---|
| 0 | `pending` (async wait) | null |
| 1 | `approved` | null |
| 2 | `failed` (sync error) | random `timeout` or `processing_error` |
| Other | `reproved` | null |

You can also push the outcome explicitly:

```bash
PATCH https://sandbox-api.malga.io/v1/charges/<CHARGE_ID>/...
{ "status": "approved" }
```

SDK equivalent:

```ts
await malga.sandbox.changeAntifraudStatus({ chargeId, status: 'reproved' });
```

## Forcing capture and refund errors

To simulate **failed capture or refund**, send the special amount **`991`** on those requests:

```bash
POST /v1/charges/{id}/capture
{ "amount": 991 }     # forces failed capture in sandbox

POST /v1/charges/{id}/void
{ "amount": 991 }     # forces failed refund in sandbox
```

Malga responds with HTTP 201 and a new `transactionRequest` of `requestStatus: failed`. The charge status does not change. See the `credit-card` skill for the error-handling pattern.

## Webhook testing tools

Sandbox webhook deliveries hit the same retry schedule and Ed25519 signature flow as production. To inspect them without writing a real receiver, use a third-party tool:

- **request.bin** — instant URL, captures requests.
- **pipedream.com** — captures, exposes the payload, can pipe through code.

Pattern:
1. Create a request bin / pipedream endpoint.
2. Register a webhook in Malga pointing at that URL.
3. Trigger an event (manual status transition).
4. Inspect the delivery.

Always test signature verification by toggling the `X-Plug-Signature` value (corrupt it) to confirm your receiver rejects bad signatures.

## Sandbox vs production differences

| Aspect | Sandbox | Production |
|---|---|---|
| Base URL | `sandbox-api.malga.io` | `api.malga.io` |
| Credentials | Separate sandbox keys | Production keys |
| Real money | No | Yes |
| Manual status push | Yes (`POST /charges/{id}`) | No |
| Test cards (last-digit rule) | Yes | No |
| Real provider integrations | Sandbox-mode of each provider | Live provider |
| Webhook retries | Same schedule | Same schedule |
| Settlement (payouts) | Simulated | Real |

## Recommended sandbox test plan

For a new merchant integration, validate these scenarios at minimum:

1. Approved card charge → `authorized`.
2. Declined card → `failed`. Verify `declinedCode`.
3. Pre-auth + capture (partial).
4. Refund (full and partial).
5. Pix charge → `pending` → manually push to `authorized` → check webhook.
6. Boleto charge → `pending` → manually push to `authorized`.
7. Antifraud `reproved` outcome (document ending in 9).
8. Capture failure with amount `991`.
9. Webhook signature verification (good and corrupted).
10. Idempotency: same `X-Idempotency-Key` returns same response.

## Pitfalls

- **Sandbox and production use different credentials.** Do not mix them. The same key never works in both environments.
- **Sandbox manual transitions are sandbox-only.** Calling `POST /charges/{id}` with `{ status }` in production has different semantics.
- **The last-digit card rule is sandbox-only.** In production, card behavior depends on the issuer.
- **Webhook receivers must be reachable from the public internet** even from sandbox. Localhost won't work; use a tunnel (ngrok, cloudflared).
- **The `991` amount trick** is intentional. Don't use `991` in production payloads for unrelated purposes.
