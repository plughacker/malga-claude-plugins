# Malga webhooks

Webhooks notify the merchant's system about asynchronous events: a charge succeeded, a session was paid, a subscription cycle failed, a payout was processed. Webhooks are the primary mechanism for keeping the merchant's database in sync with Malga.

Reference: <https://docs.malga.io/api-reference/webhooks>

## Webhook CRUD

| Action | Endpoint |
|---|---|
| List | `GET /v1/webhooks` |
| Create | `POST /v1/webhooks` |
| Detail | `GET /v1/webhooks/{id}` |
| Update | `PATCH /v1/webhooks/{id}` |
| Delete | `DELETE /v1/webhooks/{id}` |

Webhook config requires a `url`, a list of `events` to subscribe to, and a generated `secret` used for HMAC signing.

```json
POST /v1/webhooks
{
  "url": "https://api.example.com/hooks/malga",
  "events": ["charge.succeeded", "charge.failed", "subscription.cycle.failed"],
  "secret": "<auto-generated; store it>"
}
```

## Event catalog (highlights)

| Domain | Examples |
|---|---|
| Charges | `charge.created`, `charge.succeeded`, `charge.failed`, `charge.refunded`, `charge.captured`, `charge.review` |
| Sessions | `session.created`, `session.updated`, `session.paid`, `session.canceled` |
| Subscriptions | `subscription.created`, `subscription.updated`, `subscription.canceled`, `subscription.paused`, `subscription.past_due`, `subscription.cycle.succeeded`, `subscription.cycle.failed` |
| Payouts | `payout.created`, `payout.processed`, `payout.failed` |
| Customers / Cards | `customer.created`, `card.created`, `card.deleted` |

The complete list is on the API reference. Subscribe only to what the merchant's system handles — extra events generate noise and retry pressure.

## Signature verification

Every webhook delivery includes:

- `X-Malga-Signature: t=<timestamp>,v1=<hex>`
- `X-Malga-Webhook-Id` — the webhook config id
- `X-Malga-Event-Id` — unique per event delivery (use for idempotency)

`v1` is HMAC-SHA256 of `<timestamp>.<raw body>` keyed by the webhook secret. Verify with constant-time compare.

### Node (idiomatic)

```ts
import crypto from 'crypto';

function verifyMalga(signatureHeader: string, rawBody: string, secret: string) {
  const parts = Object.fromEntries(signatureHeader.split(',').map(p => p.split('=')));
  const expected = crypto
    .createHmac('sha256', secret)
    .update(`${parts.t}.${rawBody}`)
    .digest('hex');
  return crypto.timingSafeEqual(Buffer.from(parts.v1, 'hex'), Buffer.from(expected, 'hex'));
}
```

The `@malga/node` SDK provides `verifyWebhookSignature(...)` — prefer it.

## Idempotency on the receiver

Malga retries failed deliveries with exponential backoff up to ~24 hours. Duplicate deliveries can happen (network blips, receiver timeouts). Always:

1. Read `X-Malga-Event-Id`.
2. Look it up in your `processed_events` table.
3. If already processed, return `200`/`204` without doing the work again.
4. Otherwise, process and record the id.

## Retry behavior

- Initial attempt → if non-`2xx`, retried.
- Exponential backoff with jitter, capped at ~24h total.
- After max retries, the event is marked `failed` in the Dashboard. The merchant can replay it from the Dashboard.

Always return quickly — under **3 seconds**. Heavy work goes to a queue. Timeouts trigger retries.

## Designing the receiver

- Use a small router that reads the event `type`, validates signature, enqueues a job per (`eventType`, `chargeId` / `sessionId` / `subscriptionId`).
- Make handlers idempotent by id, not by content.
- Keep an audit log of every received event for at least 30 days.
- Surface delivery failures (5xx, signature mismatch) to your observability — they often indicate misconfiguration.

## Pitfalls

- **Local dev** — public HTTPS is required for webhook delivery. Use a tunnel (ngrok, cloudflared) and configure the public URL in the Malga Dashboard.
- **Signature mismatch** — usually the raw body was reparsed (JSON-stringified) before HMAC. Always sign/verify against the original byte stream.
- **Order is not guaranteed** — `charge.succeeded` may arrive before `charge.created`. Don't depend on ordering; reconcile via state.
- **Missing events** — subscribing to too few event types causes silent gaps. When in doubt, subscribe to `*` for that domain.
